# Read-only tables in ROM

For a plain-language comparison with ordinary movement and sprite animation,
read [the motion-table guide](motion-tables.md).

Use `constant_table()` for numbers that never change: animation poses, movement
paths, geometry, or lookup tables. Reading one looks like reading a normal list:

```python
orbit = constant_table([0, 4, 8, 12, 8, 4])
position = orbit[2]
last = orbit[-1]
count = len(orbit)

for offset in orbit:
    print(offset, 0, 0)
    refresh_screen()
```

The elements stay in cartridge ROM and use **zero WRAM bytes**. Pyson places
each table in a ROM bank and switches banks for reads automatically, including
reads inside functions. You do not need to select banks yourself. A read has
more overhead than a working-RAM list access, especially on banked cartridges;
this feature saves RAM rather than promising faster reads.

For values you need to change, keep using ordinary lists:

```python
enemy_health = [3, 3, 3]
enemy_health[0] -= 1
```

## Use a list as an animation path

Imagine drawing eight dots on paper to show where a character should go.
The game visits those dots in order, then starts again. A ROM table can store
those positions. It stores instructions about **where to draw**, not pictures.
The sprite artwork is a separate asset.

This complete small program uses a text marker so you can try the idea without
creating a BMP. Save it as `examples/position-path.pysn` and build it with
`npm.cmd run build -- examples/position-path.pysn position-path`.

```python
# Each pair of entries describes one position. These are text-tile coordinates.
path_x = constant_table([2, 4, 6, 8, 10, 8, 6, 4])
path_y = constant_table([4, 4, 5, 6,  6, 6, 5, 4])

step = 0
old_x = path_x[0]
old_y = path_y[0]

while True:
    print(" ", old_x, old_y)  # Erase the previous marker.
    x = path_x[step]
    y = path_y[step]
    print("*", x, y)
    refresh_screen()
    old_x = x
    old_y = y

    # Hold this position for six display frames before taking the next step.
    for delay in range(6):
        wait_vblank()
    step = (step + 1) % len(path_x)
```

At step 0, the marker is at `(2, 4)`. At step 1, it moves to `(4, 4)`.
At step 2, it moves to `(6, 5)`. The two tables must have matching lengths;
this example uses the length of `path_x` to choose the next step.
Change the numbers to change the route. Change `range(6)` to `range(12)` to
hold each position longer. The program jumps between listed positions; it
does not automatically calculate positions between them.

The same idea works with sprites: read the next x/y pair and give those values
to `sprite()`, using pixel coordinates instead of text-tile coordinates.
Use a path for a repeating enemy route, a camera tour, a bobbing collectible,
or carefully choreographed particles. Use ordinary runtime calculations when
movement must react to input, collisions, or a changing target. You can also
combine a prepared path with a changing offset.

### How Last Light scales up this idea

In [Last Light's motion module](../examples/last-light/includes/motion.pysn),
`pose_0` is the first scene's animation data. The name is ordinary example code,
not a built-in. It holds **64 snapshots of 20 particle positions**: 1,280
entries. `pose_1` through `pose_5` hold the other scenes' sequences.

A **pose** means one snapshot of the particles' arrangement. To find particle
7 in snapshot 3, the renderer reads entry `3 * 20 + 7`. Snapshot numbers and
particle numbers start at zero. It updates five particles at a time, completing
one snapshot over four drawing updates.

To save cartridge space, this particular demo combines x, y, and a near/far
appearance flag into one number per particle. `-1` hides a particle. That is
why the numbers look mysterious. It is an optional storage choice, not a Pyson
requirement. Separate x/y tables, as above, are easier to understand and edit.

These large tables were **generated by an authoring script**, not typed by hand.
The script calculated the perspective positions before the ROM was built;
the running game reads the finished numbers and draws the particles. Its output
is included in the example, so you do not need the internal generator to build
or play it. The generator is an internal development tool, not a public Pyson
motion editor. Editing one number is possible; redesigning thousands of packed
entries by hand is not a practical authoring workflow.

Prepared positions trade cartridge space for less calculation during play.
They do not respond to the player's actions unless you add logic for that.
For comparison, [Oath of Stars](../examples/oath-of-stars/README.md) rotates and
projects its geometry while the game runs instead of storing finished poses.

## Declaration and elements

Declare a table at the top level of the main file or an imported module. It
accepts one list of compile-time signed 16-bit integer expressions. Booleans,
negative values, arithmetic, and previously declared `constant()` values work:

```python
STEP = constant(4)
path = constant_table([0, STEP, STEP * 2, -STEP])
```

Runtime variables, strings, nested lists, and function calls are not elements.
Tables cannot be declared inside functions or conditional blocks. They cannot
be reassigned or modified through indexing. Trying either gives a compile error.
Table aliases and slices are not supported. Whole tables can be passed to
[array parameters](arrays.md#array-parameters), using the same helpers as mutable
integer arrays. Pyson handles the table's length and ROM bank automatically.
The compiler rejects passing a table to a parameter that the helper modifies,
including writes forwarded through other helpers. A helper may copy a ROM source
into a separate mutable target. Parameters cannot be rebound or returned.

Tables follow the existing initialization checks: place their declarations or
imports before code that reads them or calls helpers that read them. Imported
tables are included once, even when several modules import the same module.

## Passing tables to functions

A function can read a normal array or a `constant_table` in exactly the same way.
You do not need a separate version of the function for each kind.

### Choose the right kind of list

- Use a normal array, such as `[3, 3, 3]`, for numbers that can change while
  the game runs. Enemy health and inventory quantities are examples.
- Use `constant_table([3, 3, 3])` for numbers that stay the same. Starting
  inventory quantities, animation steps, and movement patterns are examples.

RAM is the Game Boy's working memory for changing values. ROM is the data stored
in the game cartridge. Keeping fixed numbers in ROM leaves more working memory
available for the rest of your game. It does not make reading them faster.

### Example 1: read either kind with one function

This complete small program adds up two lists and displays their totals:

```python
def total(values):
    result = 0
    for value in values:
        result += value
    return result

# This array can change during the game.
scores = [10, 20, 30]

# These numbers are fixed and stay in the cartridge.
weights = constant_table([2, 4, 8])

score_total = total(scores)
weight_total = total(weights)

print(score_total, 0, 0)    # Displays 60.
print(weight_total, 0, 1)   # Displays 14.
refresh_screen()
```

`values` is the name the function uses for whichever list you give it.
`total(scores)` reads `scores`; `total(weights)` reads `weights`.
Calling the function does not make another copy of the list. Pyson handles
finding the numbers in memory, including any cartridge bank changes.
You do not need to know how those banks work.

You can also use a named argument: `total(values=weights)` means the same thing.
Different calls can give the function lists of different lengths. `len(values)`
returns the length of the list given to that call. An empty list has length zero;
the loop above skips it and returns zero.

### Example 2: a function that changes values

This function works with a normal array because it changes the original numbers:

```python
def clear_items(values):
    for i in range(len(values)):
        values[i] = 0

inventory = [2, 0, 5, 1]
starting_items = constant_table([2, 0, 5, 1])

clear_items(inventory)       # Works: inventory becomes [0, 0, 0, 0].
# clear_items(starting_items)  # Uncommenting this causes a compile error.
```

A ROM table cannot change. Pyson checks this when you build the game, so it
rejects the second call before producing a ROM. It also rejects changes such as
`values[0] += 1`, and catches changes made by another function that receives
`values`. A change inside an `if` still counts, even if you expect that branch
never to run. You do not need to mark the parameter as read-only yourself.

### Example 3: reset an array using a ROM table

A function can read one list while changing another. This is useful for
resetting game state without keeping an extra set of starting values in RAM:

```python
def copy_items(target, source):
    if len(target) != len(source):
        return 0
    for i in range(len(target)):
        target[i] = source[i]
    return 1

inventory = [0, 0, 0, 0]
starting_items = constant_table([2, 0, 5, 1])
copied = copy_items(target=inventory, source=starting_items)
# inventory is now [2, 0, 5, 1]. copied is 1 because the copy succeeded.
```

Here, `target` receives the changes, so it must be a normal array. `source` is
only read, so it can be a normal array or a ROM table. If their lengths differ,
this helper returns zero and leaves the target unchanged. No `global` statement
is needed to change array elements through a parameter.

Try [Array Inventory](../examples/array-inventory.pysn), which uses this helper
when you press Start. [Tutorial 11](../tutorials/11-array-helpers.md) walks through
building it and changing its reset values.

### Rules to remember

- Create the array or table first, then pass its name: `total(weights)`.
  Passing an inline list such as `total([2, 4, 8])` is unsupported.
- Inside the helper, use `len(values)`, `values[i]`, or `for value in values`.
  Negative indices work: `values[-1]` reads the last number. Reading beyond
  either end, or reading an element of an empty list, stops the game with an error.
- A parameter lets the function use the original list. You cannot replace it
  with another list, return the whole list, or save it under another array name.
- These helpers take lists of integers. Record arrays and whole object pools
  use their own rules and cannot be passed as integer-array parameters.

The list's numbers are not copied into RAM when you pass a table. Pyson uses
six bytes of working memory for each parameter that can receive a ROM table,
or four bytes for a parameter that only receives normal arrays. These are small
fixed amounts for the helper, not an extra allocation for every call or element.

## Bounds and capacity

Indexing starts at zero. Negative indices count backward from the end.
`len(table)`, direct iteration, and truth testing work as with normal arrays.
Assigning the iteration variable changes that variable, not the table.

Literal out-of-range indices are compile errors. Dynamic invalid indices show
the existing `Index out of range` runtime message and source location, then
stop the program. Empty tables are allowed but cannot be indexed.

Each table supports at most **8,191 elements**, occupying two ROM bytes per
element and fitting entirely in one switchable ROM bank. An empty table uses
one placeholder ROM byte. Split larger data sets into separate tables.
Available cartridge capacity still limits total data. Pyson chooses MBC5
automatically if the default ROM-only configuration cannot fit; an explicitly
selected controller or ROM capacity must accommodate the data.

## Build reports and example

In the build report, table entries have `storage: "rom"`, `readOnly: true`,
`bytes: 0`, and `romBytes` showing their cartridge storage. Their bank and
address identify ROM locations. They do not contribute to named-variable WRAM
usage; loop cursors and other runtime variables still do.

[Void Engine](../examples/void-engine/README.md) uses tables for its torus poses
and orbit coordinates. Moving these three lists into ROM frees **896 WRAM
bytes** while keeping their indexing syntax and artwork unchanged.
